# 整理超时与旧摘要任务诊断（2026-10-24）

## 复现证据

用户在任务列表看到两次整理失败：`a86a39b0-b643-44e2-b34d-29bdfde92399`、`ff78203e-eca7-4a84-bea9-ceee3375430c`。从创建到结束分别约 68 秒和 67 秒。保存的聊天配置为 timeout=120 秒、max_retries=2、revision=1，但整理代码将超时改为 `min(60, saved_timeout)`，并将重试次数设为 0。

这说明整理没有遵守设置中的超时；任务耗时与该限制相符。历史错误把所有 TransportError 归为“服务连接超时或网络不可达”，没有保存异常子类，所以无法仅凭旧记录断言当时一定是 ReadTimeout 或服务端网络故障。短连接测试成功也不能证明较长的完整 JSON 生成能在同样时间内结束。

另两条旧入库任务不是已恢复后残留的虚假错误。两份文档当前均 parse/index/classification=ready，但 summary=failed，短/全文摘要为空；各有约 290 字的真实章节摘要检查点，分类已经人工应用。失败发生在最终摘要字段校验；当时未保存原始响应或字段诊断，无法追溯具体是何种字段不符。

## 修复

- 整理使用已保存的聊天超时，不再强制 60 秒；长方案仍仅发送一次模型请求，保留后台额度和聊天预留槽。
- 精简方案输入输出，缩短重复资源标识和解释；模型生成后仍恢复真实资源 ID 并重新校验权限、版本、租约和范围，审批前不修改资料。
- 网关区分响应等待、建立连接、发送请求、连接池、代理及协议错误；固定错误码和文案不包含提供方响应、地址或密钥。模型主动报告输出达到长度上限时明确报截断，避免被误标为摘要字段错误。
- 摘要独立/联合流程统一报告白名单字段及校验类型，不回显原值或任意未知键，不放宽数据校验或伪造结果。
- 整理记录读取快照、等待模型、校验方案的真实阶段及耗时；没有可测比例时不展示虚构百分比。自动重试期间的旧错误标为“上次尝试”。

HTTPX 的 read timeout 是等待下一块响应数据的最长间隔，不是整个任务的总时长。参考 [HTTPX 官方超时文档](https://github.com/encode/httpx/blob/master/docs/advanced/timeouts.md) 和 [异常分类](https://github.com/encode/httpx/blob/master/docs/exceptions.md)，通过 Context7 `/encode/httpx` 核对。
