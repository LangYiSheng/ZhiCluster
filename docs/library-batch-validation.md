# 文档批量管理优化验收

日期：2026-10-24。仅使用合成元数据、内存 SQLite 和独立评估 PostgreSQL 专库；无模型调用。保留 `POST /api/documents/batch` 的请求、返回结构与 200 条上限。

## 改动与行为边界

原接口逐文档验证权限，再逐份调用单文档更新。200 份文档会重复读取知识库、成员、文档、目录和标签；恢复时，设置删除状态后查询父目录还会提前触发一次自动 flush，随后增加版本又更新一次。

新增批量服务按以下顺序执行：

1. 在当前知识库取得一次命名空间锁，校验编辑权限。
2. 只锁定本库请求文档，按 ID 排序取锁并刷新已有身份缓存。非法 ID、外库 ID 和权限错误使整笔请求失败；不先取得其他知识库文档的锁。
3. 批量校验移动目标、恢复所需的父目录及目标标签。所有资源校验完成后才修改数据，避免恢复的提前写入。
4. 一次读取当前标签快照，按 `set`、`add`、`remove` 计算关联差量；保留未变化的关联，仅批量删除不再需要的关联、添加缺少的关联。
5. 统一 flush 文档版本和元数据，再为每份文档保存独立的 before/after 审计；返回值保持请求中首次出现的文档顺序。

同一批请求中的重复 ID 只更新、审计一次。原接口中无变化的有效操作仍增加一次版本并产生审计，此语义保留。移动到根目录使用 `folder_id: null`，清空标签使用空列表；无效空目录 ID 仍返回 400。任何资源校验或事务提交失败都不应留下部分修改。

## 合成 SQL 与耗时基准

旧实现基线为提交 `b6bfcea` 下的接口，数据是 200 份文档、每份一个原标签，另有一个目标目录和新标签；SQLite 开启真实外键。通过 TestClient 调用完整 HTTP 接口，每类操作 3 次。新脚本使用同一数据规模和接口路径。

```powershell
backend/.venv/Scripts/python scripts/library_benchmark.py --include-batch --repeats 3 --output .data/library-benchmark/batch-after.json
```

`--include-batch` 只追加独立的 `batch` 结果；原有目录展开、文档分页和子树删除的默认基准、输出字段与数据口径保持原样。旧批量探针保存在忽略目录 `.data/batch-diagnostic.py`，原始结果为 `.data/batch-diagnostic.json`；新结果为 `.data/library-benchmark/batch-after.json`。

| 200 文档操作 | 原 SELECT | 新 SELECT | 原 UPDATE 调用 | 新 UPDATE 调用 | 原耗时中位 | 新耗时中位 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 移动 | 2,402 | 7 | 200 | 1 | 494.608 ms | 46.574 ms |
| 添加标签 | 2,602 | 7 | 200 | 1 | 659.849 ms | 51.901 ms |
| 移入回收站 | 2,202 | 6 | 200 | 1 | 432.258 ms | 42.307 ms |
| 恢复 | 2,402 | 7 | 400 | 1 | 497.779 ms | 48.317 ms |

这里统计数据库游标执行次数。新 UPDATE 使用批量执行，仍更新 200 份文档各自的版本，并保留 200 条审计；不是只更新一份资源。添加标签不再执行 200 次先删除全部关联的 DELETE，新关联和审计各批量插入一次。

计时只代表本机内存 SQLite 合成元数据及当时负载，包含 TestClient 请求处理，不代表真实 PostgreSQL 网络时延、文件内容处理或系统整体加速。一次回收样本有约 183 ms 的波动，表格使用规定的 3 次中位，原始样本完整保留。SQL 次数和状态正确性由独立回归测试验证。

## 正确性回归

新增 `test_library_batch.py` 覆盖 200 文档的移动、标签三种模式、回收和恢复，限制每批 SELECT 不超过 15 次，并检查逐文档版本、审计和返回顺序。原实现先运行这组测试，6 种操作都因 2,202 至 2,602 次 SELECT 失败；其余已有语义先通过，再实现优化。

另外覆盖非法文档 ID、混入可读外库文档、无效标签、无效目录和已删除恢复父目录的整笔回滚；重复 ID 去重、无变化操作的版本语义、单文档旧版本冲突；标签差量和清空不影响未选文档；根目录移动、只读成员拒绝写入与 201 项请求拒绝。

## 真实 PostgreSQL 等待竞态

`test_library_batch_postgres.py` 在独立评估容器的 `zhicluster_ingestion_test` 专库运行，5 种情况均通过。每次先由另一事务持有知识库锁，让批量操作保留旧文档、目录和标签的身份缓存后等待，再提交并发变化：

- 先移动一份文档并增加标签，同时软删除另一份文档：后续批量加标签保留最新目录、并发标签和删除状态，审计 before 使用最新版本。
- 删除目标目录：整批拒绝，文档版本和审计不变。
- 删除目标标签：整批拒绝，未覆盖原关联。
- 移除一份请求文档：整批返回不存在，其余文档不改变。
- 恢复等待期间父目录被删除：整批拒绝恢复。

```powershell
# 将 PG_INGESTION_TEST_URL 设置为独立专库连接，库名必须为 zhicluster_ingestion_test。
cd backend
.venv/Scripts/python -m pytest tests/test_library_batch_postgres.py -q -p no:cacheprovider
```

这些测试不使用日常数据库，也不重启正在执行检索基线的评估 API。SQLite 不证明 PostgreSQL 行锁正确性，锁等待结论仅由上述真实数据库测试支持。
