# 检索分页与长文档候选准入：第二轮评估

日期：2026-10-24。比较基线为首轮检索改进 `ffe53e2`。所有候选方案先在忽略目录中的可信模块快照运行，确认质量、深页容量和长文档风险后才修改产品检索模块。主任务完成旧 API 的中文全量基线后重建隔离 API，再验证 600 方案；没有调用真实模型。

## 实际问题与边界

旧候选预算由 `limit + offset` 决定：总池为 `min(600, max(160, requested * 8))`，每文档上限为 `min(100, max(12, requested))`。分页时新增的候选会改变 IDF 和多样性排序，导致已经翻过的结果移动到后页。

在 25 份文档、每份 20 个片段的确定性语料中复现重复/漏项，并缩小到两份文档各 13 个片段的样本：第一次 `limit=10` 的末项在第二次 `limit=10, offset=10` 中再次出现，新增片段则移动到已经翻过的前 10 项。仅检查“page2 等于一次取前 20 项的后 10 项”不足以发现问题，因为两次请求的 requested 同为 20；必须检查实际 page1 + page2 的拼接。

当前搜索弹窗固定取前 25 条，没有分页控件。本轮修复直接搜索 API 的静态分页行为，为未来分页交互提供正确基础。

API 参数仍允许 `limit=1..100`、`offset=0..10000`，排序窗口仍最多 600 项；`offset >= 600` 返回空列表。`total` 表示受限候选窗口的结果数，不能解释为全库的全部匹配数量。没有把窗口缩小成 240 来换取表面稳定。

## 训练样本比较

使用 SciFact 和 NFCorpus 各自 train 按 query ID 排序的前 60 条，完整语料不抽样，关键词模式且不调用模型。指标定义、公开来源、许可和脚本见[首轮检索评估](retrieval-benchmark-validation.md)。耗时是本机有后台任务时的观测，不能用作普遍加速或减速比例。

| 数据集 | 候选预算 / 每文档上限 | Recall@10 | MRR@10 | nDCG@10 | 中位耗时 |
| --- | --- | ---: | ---: | ---: | ---: |
| SciFact | 动态（前 10 项为 160 / 12） | 0.819444 | 0.704861 | 0.723189 | 381.485 ms |
| SciFact | 固定 240 / 30 | 0.819444 | 0.698909 | 0.718444 | 388.960 ms |
| SciFact | 固定 600 / 100 | 0.836111 | 0.710317 | 0.731439 | 453.520 ms |
| NFCorpus | 动态（前 10 项为 160 / 12） | 0.095522 | 0.394074 | 0.267661 | 78.475 ms |
| NFCorpus | 固定 240 / 30 | 0.095527 | 0.391667 | 0.266456 | 91.200 ms |
| NFCorpus | 固定 600 / 100 | 0.095465 | 0.382778 | 0.265027 | 88.000 ms |

240 / 30 的排序指标略降，而且在 500 片段样本的 offset=240 处返回空，原方案仍能返回 10 项，因此排除。600 / 100 在两份训练语料上的效果不同，继续完整 test 验证，没有只展示 SciFact 的改善。

这次完整 test 中，两份语料的三项平均指标均提高。SciFact 观测中位耗时为 333.290 → 465.025 ms，NFCorpus 为 85.920 → 87.960 ms。扩大准入会读取和计算更多候选，不宣称这是没有成本的改进。

BEIR 脚本每份摘要只有一个片段，不能验证长 PDF 是否挤占候选池。因此补充 20 份文档各 100 个片段的压力样本，所有片段包含相同的三个查询词，第 11 份文档有一段更短、词频更高的目标证据：

- 原动态预算下，目标排第一，前 10 条来自 10 份文档。
- 直接固定 600 / 100 时，同分候选按片段 ID 截断，前 6 份长文占满 600 个名额，目标丢失，前 10 条只覆盖 6 份文档。这种方案没有直接进入产品。
- 最终在 SQL 主相关性相同时，先按文档内候选序号、再按片段 ID 稳定准入，目标恢复第一，前 10 条覆盖 10 份文档。主词面相关性/向量距离仍是第一排序键，文档分散不会把低相关候选放到高相关候选之前。

最终方案是固定 600 / 100，并在相同主相关性内均匀准入。BEIR 的每文档候选序号恒为 1，因此最后这个同分调整在上述完整 test 语料上与固定 600 快照排序相同；实际重跑两份 train60 均逐项得到相同平均指标。多片段行为由独立压力样本、静态分页和真实 PostgreSQL 专项验证。

## 全部 3,219 条中文问题的真实 API 对照

同一 CMRC2018 开发集的 848 份真实入库资料，3219 条问题全部执行，固定 seed=20261024、limit=30、关键词模式、无模型。逐项校验数据 SHA、题序、问题 ID、原问题、预期来源 key 和答案列表一致；两份记录均为 3219 个唯一问题，HTTP 传输重试均为 0。

基线镜像 revision 为 `sha256:e06401d0951b9ae5…`，600 方案镜像为 `sha256:33a7f3553df034ef…`。完整值保存在原始结果，比较对象不是不同抽样或运行中混合版本。

| 指标 | 旧动态预算 API | 600 + 同分分散 API | 逐题变化 |
| --- | ---: | ---: | --- |
| 来源 Recall@1 | 0.963964 | 0.963964 | 3219 条均不变 |
| 来源 Recall@5 | 0.994719 | 0.994719 | 3219 条均不变 |
| 来源 Recall@10 | 0.996893 | 0.996893 | 3219 条均不变 |
| 来源 MRR@10 | 0.977630956 | 0.977501516 | 2 条降低、3217 条不变、0 条提高 |
| 前 5 个片段含正确来源及答案 | 0.990059 | 0.990059 | 3219 条均不变 |

目标来源排名发生变化的只有：

- `DEV_508_QUERY_2`（北京地铁 4 号线和 10 号线换乘方式）：第 2 → 第 3，正确答案仍在前 5 个片段。
- `DEV_554_QUERY_0`（城巴 7 号线是什么线路）：第 2 → 第 4，正确答案仍在前 5 个片段。

其余候选也有重排：283 条问题的前 10 文档序列变化，139 条前 10 文档集合变化，62 条前 5 文档集合变化；首位文档在全部 3219 条中均不变。因此不能把目标来源指标基本保持解释为所有候选顺序都不变。

本次 MRR 平均下降 0.000129440，即约 0.012944 个百分点，来源召回和答案证据没有新增损失。结合静态分页不重不漏、保持 600 条深页容量及英文完整 test 的改善，接受这项分页正确性修复；不把它描述为中文检索质量全面提高。两个排名倒退样本和原有 32 条答案@5缺失样本保留为后续独立优化对象，没有因平均值接近就丢弃。

HTTP 耗时中位数两次均为约 172 ms，p95 为约 485 → 500 ms。运行期间的后台负载不同，记录原始观测，不将其全部归因于候选预算。原始结果为 `.data/continuous-optimization/cmrc-pre-pagination-full.json` 与 `cmrc-pagination-full.json`，逐题比较为 `cmrc-pagination-comparison.json`。

## 验证与非稳定边界

产品改动保持原始片段、引用锚点、权限/标签/文件夹复核及最多 600 条排序窗口。没有增加模型调用或缓存，也没有改变数据库结构。

- 聚焦检索、分页、证据筛选、主动检索、聊天进度及堆排序回归：104 项通过。
- 新增 SQLite 分页回归 5 项：26 片段最小样本、500 片段连续分页、offset=240/490 深页、2,000 片段长文目标保护、主相关性优先。
- 专用 PostgreSQL `127.0.0.1:25432/zhicluster_ingestion_test`：4 项通过，包含真实 SQL 静态分页和深页、关键词长文准入、受控相等 cosine 向量的准入排序、主相关性优先。受控向量不代表真实模型检索质量。测试数据在事务结束后回滚，不创建原文件。
- Ruff 和 diff 空白检查通过。中文真实 API 的两个镜像与全部 3219 条逐题比较见上一节；这些结果不验证之后的 SQL CTE 重构，后者有独立的只读性能及范围门禁记录。

稳定性适用于相同语料、范围、配置和确定性排序下的分页。`rerank=true` 会每页重新执行可选模型筛选；模型输出变化、资料变更、权限变更或配置变化仍可能改变结果。没有将静态候选预算修复描述为跨这些变化的绝对快照保证。若以后要求这种保证，需要查询快照/游标和取页时的权限复核。

原始快照、训练/完整 test 结果和分页压力样本位于 `.data/retrieval-benchmark/candidate-budget/`、`*-budget-*.json`、`pagination-probe-*.json` 和 `long-document-*.json`；它们均为忽略目录中的测试证据，不包含用户日常资料。
