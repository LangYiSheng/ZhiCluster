# 联合入库与集中整理审阅验收（2026-10-24）

## 改动范围

- 短文档摘要、分类由原先两次顺序请求合并为一次结构化请求，分别校验、提交结果。长文档按预算打包最多 8 个章节并行摘要，再联合生成最终摘要与分类。失败只补缺失阶段，已完成章节有检查点。
- 解析、分块与索引先提交，再执行可选的摘要和分类；列表显示可检索及后台阶段，Reader 不等待元数据。整理方案走后台任务通道及模型额度，保留交互槽；限额为 1 时无法预留，模型服务自身的账户级拥塞也不能由本地队列消除。
- 分块使用 token 偏移窗口，保护可容纳的代码块和表格边界，较大表格优先按行拆分。Markdown 代码块中的 `#` 不作为标题。新建或缺失向量增加有界的章节路径、文件名和续表表头上下文，原文及引用定位不变。
- 新增“整理审阅”页，跨知识库集中筛选、编辑和审批分类建议。批量逐项报告冲突；过期建议可以只重跑分类。应用建议保留人工标签，使用审计与可撤销的事务执行器。
- 自动整理现有资料：选择知识库及至多 50 份文档，JSON 模型生成目录、移动和追加标签方案；用户可编辑、取消部分操作、批准、拒绝及撤销。生成方案不修改资料，不依赖工具调用能力。

## 性能边界

受控 12 节长文样例只需要 2 次章节分组请求及 1 次最终联合请求；这证明请求合并行为，不能推导任何提供方的固定延迟倍数。

同一进程预热 tokenizer、45,000 字符重复中文资料、默认分块参数、各运行 3 次：改前中位数 277.38 ms，改后 46.57 ms，两者均为 58 块。结果来自 `.data/enrichment-review/chunking-comparison.json`，是局部 CPU 分块基准，未包括解析、数据库、向量或模型网络时间，不代表全部入库加速倍数。

旧文档不自动重切块或重建全部向量；这次改动不改变已保存模型配置、密钥或 profile fingerprint。现有向量若需全部采用上下文输入，仍需后续提供明确的全量重建操作。
